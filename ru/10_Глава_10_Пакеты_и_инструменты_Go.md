## 10.1. Почему компилятор Go работает быстро

1. **Явные импорты в заголовке файла**: Компилятору не нужно парсить тело файла, чтобы составить граф зависимостей.
2. **Строгий запрет циклических зависимостей**: Граф импортов всегда является направленным ациклическим графом (**DAG**), что позволяет собирать независимые пакеты параллельно на всех ядрах CPU.
3. **Самодостаточные объектные файлы**: Скомпилированный объектный файл пакета уже содержит метаданные о всех его экспортированных зависимостях. Компилятору достаточно прочесть ровно один файл на каждый импорт.

## 10.2. Пути импорта и имена пакетов

Каждый исходный файл `.go` начинается с директивы `package <name>`.

* **Стандартная библиотека**: короткие пути (`"fmt"`, `"net/http"`, `"bytes"`).
* **Сторонние библиотеки**: пути с префиксом хостинга (`"github.com/lib/pq"`).
* **Правило совпадения**: Имя пакета совпадает с последним сегментом пути (для `"encoding/json"` $\to$ `package json`).
* **Исключения**:
  * `package main` — точка входа исполняемого бинарного файла.
  * `package foo_test` — внешний тестовый пакет (разрывает циклические зависимости тестов).

```go
import (
    "crypto/rand"
    mrand "math/rand" // алиас для устранения коллизии имен
)
```

## 10.3. Пустой импорт (Blank Import `_`)

> Неиспользуемый импорт в Go запрещен компилятором.

**Пустой импорт** `import _ "path"` подключает пакет **исключительно ради побочного эффекта** — запуска функций `init()` и регистрации драйверов.

### Паттерн саморегистрации (Registration Pattern)

```go
// 1. Автоматическая регистрация декодеров изображений в image.RegisterFormat:
import (
    "image"
    _ "image/png"
    _ "image/jpeg"
)
img, format, err := image.Decode(r) // само определит PNG или JPEG

// 2. Регистрация драйвера базы данных в database/sql:
import (
    "database/sql"
    _ "github.com/lib/pq" // регистрирует драйвер "postgres"
)
db, err := sql.Open("postgres", dataSourceName)
```

## 10.4. Соглашения об именовании пакетов

> [!TIP]
> **Имена пакетов должны быть**:
> * Короткими, строчными, в единственном числе: `bytes`, `json`, `sync`, `time`, `http`.
> * Описательными: `imageutil` или `ioutil` предпочтительнее невнятного `util`.

### Избегайте «заикания» (Stuttering)

Поскольку вызовы функций всегда включают имя пакета, имя сущности внутри пакета не должно повторять его название:

| Антипаттерн | Стиль Go | Вызов в коде |
| :--- | :--- | :--- |
| `http.HttpClient` | `http.Client` | `client := http.Client{}` |
| `bytes.ByteBuffer` | `bytes.Buffer` | `buf := bytes.Buffer{}` |
| `json.JSONMarshal` | `json.Marshal` | `json.Marshal(v)` |
| `rand.RandInt` | `rand.Int` | `rand.Int()` |

## 10.5. Инструментарий CLI (`go tool`)

* `go build` — компиляция пакета (для `package main` создает исполняемый файл в текущей папке).
* `go run main.go` — компиляция во временный каталог (с кешем сборки) и немедленный запуск.
* `go install` — сборка с сохранением исполняемого файла в `$GOBIN` (по умолчанию `$HOME/go/bin`) для доступа из терминала.
* `go get <path>` — **добавление/обновление зависимости в `go.mod`** (с Go 1.18 не собирает и не устанавливает бинарники).

> [!NOTE]
> **Актуальность (модули Go):** во времена книги (`GOPATH`) `go get` скачивал и устанавливал пакеты целиком. Сегодня зависимости описывает `go.mod`: `go get`, `go mod tidy`, `go mod download`. Установка инструментов командной строки — отдельная команда с версией: `go install golang.org/x/tools/cmd/goimports@latest` (суффикс `@version` обязателен вне модуля, начиная с Go 1.16).

### Встроенная кросс-компиляция

Сборка под любую операционную систему и архитектуру процессора без сторонних тулчейнов:

```bash
GOOS=linux GOARCH=arm64 go build -o myapp-arm64
GOOS=windows GOARCH=amd64 go build -o myapp.exe
```

### Условная компиляция (Build Tags)

1. **По суффиксу имени файла**: `file_linux.go`, `file_windows.go`, `asm_amd64.s`.
2. **По тегам сборки в заголовке файла**:
   ```go
   //go:build linux || darwin
   ```
   В книге использовался старый синтаксис `// +build` — он устарел (Go 1.17+); `gofmt` синхронизирует обе формы автоматически.

## 10.6. Внутренние пакеты (`internal`)

Механизм сокрытия вспомогательного кода внутри модуля:
* Пакет, содержащий каталог `internal` в пути (например, `net/http/internal/chunked`), может быть импортирован **только пакетами, находящимися в том же родительском дереве** (`net/http/...`).
* Любой сторонний пакет при попытке импорта получит ошибку компиляции.

## 10.7. Документирование (`godoc`)

* Комментарий, расположенный непосредственно перед экспортируемым объектом, автоматически преобразуется в документацию.
* Первое предложение комментария должно начинаться с имени документируемого объекта:
  ```go
  // Fprintf formats according to a format specifier and writes to w.
  func Fprintf(w io.Writer, format string, a ...any) (int, error)
  ```
* Консольный просмотр: `go doc http.Client.Do`.
* Локальный веб-сервер: `godoc -http=:8000`.

> [!NOTE]
> **Актуальность:** автономная утилита `godoc` **удалена из дистрибутива Go** (начиная с Go 1.12). Веб-просмотр сегодня: онлайн `pkg.go.dev` или локально `go run golang.org/x/pkgsite/cmd/pkgsite@latest`; консольный `go doc` работает как прежде.
