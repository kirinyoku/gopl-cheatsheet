## 8.1. Горутины (Goroutines)

Go использует модель **CSP**: независимые параллельные задачи (горутины) общаются через каналы сообщений, не разделяя память напрямую.

> *«Не общайтесь через разделяемую память; разделяйте память через общение».*

### Базовые правила

* **Запуск**: Ключевое слово `go` перед вызовом функции:
  ```go
  go doWork() // выполняется асинхронно в новой горутине
  ```
* **Главная горутина**: Функция `main()` работает в главной горутине. Когда `main()` завершается, **все остальные фоновые горутины принудительно уничтожаются**.
* **Отсутствие внешнего прерывания**: В Go нет механизма принудительного прерывания или завершения горутины извне. Она должна корректно завершаться сама по сигналу.

## 8.2. Каналы (Channels)

Канал — это потокобезопасный типизированный механизм для передачи данных и синхронизации:

```go
ch := make(chan int) // создание небуферизованного канала
ch <- 42             // отправка в канал
v := <-ch            // прием из канала
close(ch)            // закрытие канала
```

### 1. Небуферизованные каналы (Синхронные)

* `make(chan int)` — емкость буфера равна 0.
* **Принцип рандеву**:
  * Отправка блокируется, пока получатель не начнет читать.
  * Чтение блокируется, пока отправитель не запишет значение.
  * Обеспечивает строгое отношение предшествования событий (**happens-before**).

### 2. Буферизованные каналы (Асинхронные)

* `make(chan string, 3)` — емкость буфера 3.
* Отправка блокируется **только при переполнении буфера**.
* Чтение блокируется **только при пустом буфере**.

> [!CAUTION]
> **Утечка горутин (Goroutine Leak)**:  
> Если горутина зависает при отправке в небуферизованный канал, который больше никто не читает, она **остается в памяти навсегда**. Сборщик мусора **не удаляет** заблокированные горутины!  
> *Пример решения*: использовать буферизованный канал на точное число ответов (`make(chan string, 3)`).

## 8.3. Конвейеры (Pipelines) и правила закрытия каналов

Горутины часто соединяются в конвейеры, где вывод одной горутины становится входом другой:

```go
// Чтение всех элементов до момента закрытия канала:
for x := range ch {
    fmt.Println(x)
}
```

### Правила работы с закрытыми каналами:

1. Запись в закрытый канал $\to$ **ПАНИКА**.
2. Повторное закрытие закрытого канала $\to$ **ПАНИКА**.
3. Чтение из закрытого канала: сначала вычитываются оставшиеся значения, затем возвращается нулевое значение (`zero value`) без блокировки.
4. Проверка закрытия: `val, ok := <-ch` (`ok == false`, если канал закрыт и пуст).

> [!IMPORTANT]
> Закрывать канал должен **только отправитель** и только тогда, когда получателю необходимо явно передать сигнал о завершении потока данных.

## 8.4. Однонаправленные каналы

Ограничивают права доступа к каналу в сигнатурах функций:
* `chan<- int` — канал **только для отправки** (`send-only`). Нельзя читать.
* `<-chan int` — канал **только для чтения** (`receive-only`). Нельзя писать, нельзя закрывать.

```go
func generate(out chan<- int) {
    for i := 0; i < 10; i++ { out <- i }
    close(out)
}

func printValues(in <-chan int) {
    for val := range in { fmt.Println(val) }
}
```

## 8.5. Синхронизация параллельных задач (`sync.WaitGroup`)

Когда число параллельных задач неизвестно заранее:

```go
func processFiles(filenames []string) {
    var wg sync.WaitGroup

    for _, f := range filenames {
        wg.Add(1) // инкремент счетчика ДО старта горутины!
        go func(name string) {
            defer wg.Done() // декремент при выходе
            process(name)
        }(f) // передача переменной цикла по значению!
    }

    wg.Wait() // ожидание обнуления счетчика
}
```

> [!NOTE]
> **Актуальность (Go 1.22+):** передача `f` параметром больше не обязательна — в модуле с директивой `go 1.22`+ замыкание может захватывать переменную цикла напрямую (`go func() { process(f) }()`), так как на каждой итерации создаётся новая переменная. Для старых версий приём выше остаётся обязательным.

## 8.6. Ограничение параллелизма (Считающий семафор)

Для защиты от исчерпания системных ресурсов (например, лимита открытых файлов/сокетов) параллелизм ограничивают буферизованным каналом:

```go
// Семафор максимум на 20 одновременных горутин:
var sema = make(chan struct{}, 20)

func crawl(url string) []string {
    sema <- struct{}{}        // захват маркера (ждет, если заняты все 20)
    defer func() { <-sema }() // гарантированное освобождение маркера

    return fetch(url)
}
```

> [!NOTE]
> **Актуальность:** в реальных проектах ограничение параллелизма чаще оформляют через `golang.org/x/sync/errgroup`: `group.SetLimit(20)` + `group.Go(...)` — тот же механизм с пробросом ошибок и ожиданием `group.Wait()`. Для захвата N единиц ресурса есть взвешенный семафор `semaphore.Acquire(ctx, n)` из того же модуля.

## 8.7. Мультиплексирование с помощью `select`

`select` позволяет ожидать событий сразу на множестве каналов:

```go
select {
case msg := <-ch1:
    fmt.Println("Получено из ch1:", msg)
case ch2 <- outMsg:
    fmt.Println("Отправлено в ch2")
case <-time.After(5 * time.Second):
    fmt.Println("Тайм-аут 5 секунд")
default:
    fmt.Println("Неблокирующая ветка: ни один канал не готов")
}
```

### Свойства `select`:

* Если готовы несколько веток, Go выбирает одну **псевдослучайно** (для равномерного обслуживания каналов).
* `select {}` блокирует горутину навсегда.
* Канал со значением `nil` в `select` никогда не будет выбран (удобно для динамического отключения веток).

## 8.8. Широковещательная отмена (Cancellation)

Лучший паттерн отмены группы горутин — **закрытие общего сигнального канала `done`**:

```go
var done = make(chan struct{})

func cancelled() bool {
    select {
    case <-done:
        return true // канал закрыт -> сигнал отмены
    default:
        return false
    }
}

// Вызов отмены (например, при сигнале ОС или ошибке):
close(done) // ВСЕ слушатели моментально разблокируются!
```

> [!NOTE]
> **Актуальность:** в современном Go отмена оформляется через пакет `context` (появился после издания книги, Go 1.7): `ctx, cancel := context.WithCancel(context.Background())`, горутины слушают `<-ctx.Done()` — тот же принцип закрытого канала, но со стандартным API, тайм-аутами (`WithTimeout`, `WithDeadline`) и переносом значений. Паттерн с `done` полезен для понимания базовой механики отмены.
