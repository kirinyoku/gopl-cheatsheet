## 9.1. Состояния гонки (Data Races)

> [!CAUTION]
> **Гонка данных (Data Race)** возникает, когда две или более горутины одновременно обращаются к одной ячейке памяти, и **хотя бы одно из обращений является записью**.

* **Одновременное чтение**: безопасно.
* **Чтение + Запись** или **Запись + Запись**: приводят к искажению данных или паникам рантайма.
* *Для многословных структур* (`slice` из 3 слов, `string` из 2 слов, `interface` из 2 слов) гонка может обновить только половину дескриптора, порождая указатель в произвольную память.

> **Аксиома Go**: *«Не существует понятия доброкачественной гонки данных (benign data race)»*. Любая гонка данных является критическим багом.

### 3 способа предотвращения гонок:

1. **Иммутабельность (Immutability)**: Инициализация структур до старта горутин и дальнейшая работа исключительно на чтение.
2. **Изоляция переменной (Confinement)**: Переменная принадлежит только одной горутине-монитору. Доступ к ней остальные получают строго через каналы.
3. **Взаимное исключение (Mutual Exclusion)**: Доступ разрешен многим горутинам, но строго по очереди через мьютексы.

## 9.2. Взаимные исключения (`sync.Mutex`)

```go
var (
    mu      sync.Mutex
    balance int
)

func Deposit(amount int) {
    mu.Lock()
    defer mu.Unlock()
    balance += amount
}

func Balance() int {
    mu.Lock()
    defer mu.Unlock()
    return balance
}
```

### Правила работы с мьютексами:

* **Всегда используйте `defer mu.Unlock()`**: Гарантирует разблокировку при любом выходе и при возникновении паники.
* **Мьютексы в Go НЕ реентерабельны**: Попытка повторно захватить мьютекс из той же горутины приведет к **взаимоблокировке (Deadlock)**.
* **Паттерн разделения функций**: Внутренняя логика выносится в неэкспортированные функции без захвата лока (например, `deposit(amount)`), которые вызываются из внешних функций с локом.

## 9.3. Мьютексы чтения/записи (`sync.RWMutex`)

Реализует паттерн *Multiple Readers / Single Writer*:

```go
var (
    mu      sync.RWMutex
    balance int
)

func Balance() int {
    mu.RLock() // параллельное неблокирующее чтение
    defer mu.RUnlock()
    return balance
}

func Deposit(amount int) {
    mu.Lock()  // эксклюзивная блокировка на запись
    defer mu.Unlock()
    balance += amount
}
```

> [!TIP]
> `sync.RWMutex` эффективен только при **подавляющем преобладании операций чтения** над записью в условиях высокой конкуренции. В простых сценариях обычный `sync.Mutex` быстрее.

## 9.4. Видимость памяти (Memory Visibility)

Примитивы синхронизации нужны не только для ожидания, но и для **гарантии видимости изменений**:
* Современные CPU переупорядочивают инструкции и кэшируют данные в локальных регистрах ядер.
* Операции с мьютексами и каналами создают **барьеры памяти (Memory Barriers)**, принудительно синхронизируя кэши процессора с оперативной памятью.

## 9.5. Отложенная инициализация (`sync.Once`)

Потокобезопасная инициализация синглтонов и тяжелых ресурсов без самодельных блокировок:

```go
var (
    loadIconsOnce sync.Once
    icons         map[string]image.Image
)

func Icon(name string) image.Image {
    loadIconsOnce.Do(loadIcons) // гарантированно выполнится ровно 1 раз
    return icons[name]
}
```

> [!NOTE]
> **Актуальность (Go 1.21+):** для типовых случаев есть хелперы без ручной пары «`sync.Once` + переменная»: `sync.OnceFunc(f)`, `sync.OnceValue(f)` (кэширует результат), `sync.OnceValues(f)` (результат + ошибка). Пример: `var config = sync.OnceValue(loadConfig)`.

## 9.6. Детектор гонки (Race Detector)

Встроенный динамический инструмент поиска гонок данных:

```bash
go test -race ./...
go run -race main.go
go build -race
```

* Записывает события доступа к памяти и выводит точный стек конфликтующих горутин при обнаружении несогласованной записи.

## 9.7. Параллельный кэш без дубликатов (Singleflight)

Идиоматичный паттерн мемоизации: пока первая горутина вычисляет результат для ключа, все последующие ждут ее завершения через закрытие канала `ready`, не создавая лишней нагрузки:

```go
// Поля Memo: mu sync.Mutex; cache map[string]*entry; f func(key string) (any, error)
type entry struct {
    res   result
    ready chan struct{} // закрывается, когда результат готов
}

func (memo *Memo) Get(key string) (any, error) {
    memo.mu.Lock()
    e := memo.cache[key]
    if e == nil {
        e = &entry{ready: make(chan struct{})}
        memo.cache[key] = e
        memo.mu.Unlock()

        e.res.val, e.res.err = memo.f(key) // вычисление
        close(e.ready)                     // оповещение всех ожидающих
    } else {
        memo.mu.Unlock()
        <-e.ready // ожидание готового результата
    }
    return e.res.val, e.res.err
}
```

> [!NOTE]
> **Актуальность:** готовая реализация паттерна — `golang.org/x/sync/singleflight`: `g.Do(key, fn)` дедуплицирует параллельные вызовы с одинаковым ключом и возвращает всем общий результат (есть и канал-ориентированный `DoChan`).

## 9.8. Горутины (Goroutines) vs Потоки ОС (OS Threads)

| Характеристика | Поток ОС (OS Thread) | Горутина (Goroutine) |
| :--- | :--- | :--- |
| **Размер стека** | Фиксированный (~1–2 МБ) | Динамический (начинается с **2 КБ**, растет до **1 ГБ**) |
| **Масштабируемость** | Тысячи потоков | **Сотни тысяч и миллионы горутин** |
| **Планирование** | Ядро ОС (вытесняющее) | Рантайм Go (**m:n планировщик**, мультиплексирование $M$ горутин на $N$ потоков) |
| **Переключение контекста** | Дорогое (системные вызовы, регистры, TLB) | Дешевое (в пространстве пользователя) |
| **Идентификатор (ID)** | Есть `Thread ID` | **Намеренно отсутствует Goroutine ID** |

### Почему у горутин нет Goroutine ID

Создатели языка специально не предоставили идентификатор горутины, чтобы предотвратить создание скрытого контекста через Thread-Local Storage (TLS). В Go все зависимости и контексты передаются **явно** (`context.Context`).

> [!NOTE]
> **Актуальность (Go 1.14+):** горутины стали **асинхронно вытесняемыми**: плотный цикл без вызовов функций больше не может надолго блокировать другие горутины и GC (во времена книги вытеснение происходило только в точках безопасного прерывания — при вызовах функций).
