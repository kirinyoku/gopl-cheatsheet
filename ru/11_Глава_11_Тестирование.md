## 11.1. Инструмент `go test`

Подход Go к тестированию минималистичен: нет тяжелых сторонних фреймворков и сложных DSL. Все тесты пишутся на чистом Go в файлах с суффиксом `*_test.go`.

* Файлы `*_test.go` **игнорируются** при сборке `go build` и компилируются **только** утилитой `go test`.
* В `*_test.go` поддерживаются 4 вида функций:
  1. `TestXxx(t *testing.T)` — функциональные и интеграционные тесты.
  2. `BenchmarkXxx(b *testing.B)` — бенчмарки производительности.
  3. `ExampleXxx()` — исполняемые примеры документации.
  4. `FuzzXxx(f *testing.F)` — нативный фаззинг (добавлен в Go 1.18, после издания книги).

## 11.2. Тестовые функции (`TestXxx`)

```go
func TestIsPalindrome(t *testing.T) {
    if !IsPalindrome("kayak") {
        t.Errorf(`IsPalindrome("kayak") = false, want true`)
    }
}
```

### Методы `*testing.T`:
* `t.Error(...)` / `t.Errorf(...)` — фиксирует ошибку, помечает тест проваленным, но **продолжает выполнение остальных проверок** (позволяет увидеть полную картину сбоев).
* `t.Fatal(...)` / `t.Fatalf(...)` — фиксирует ошибку и **немедленно прерывает текущий тест** (используется при критических сбоях предусловий).
* `t.Logf(...)` — запись отладочных сообщений (выводится при ошибке или с флагом `-v`).

## 11.3. Табличные тесты (Table-driven Tests)

Идиоматический стандарт написания тестов в экосистеме Go:

```go
func TestIsPalindrome(t *testing.T) {
    tests := []struct {
        input string
        want  bool
    }{
        {"", true},
        {"a", true},
        {"kayak", true},
        {"A man, a plan, a canal: Panama", true},
        {"palindrome", false},
    }

    for _, tc := range tests {
        if got := IsPalindrome(tc.input); got != tc.want {
            t.Errorf("IsPalindrome(%q) = %v, want %v", tc.input, got, tc.want)
        }
    }
}
```

### Флаги запуска `go test`:
* `go test -v` — подробный вывод каждого теста и времени выполнения.
* `go test -run="French|Canal"` — фильтрация тестов по регулярному выражению имени.

> [!NOTE]
> **Актуальность:** современная табличная структура теста включает поле `name` и запускает каждый кейс как **подтест** через `t.Run(tc.name, func(t *testing.T) { ... })` (Go 1.7, после издания книги): читаемые имена сбоев, точечный перезапуск (`-run TestX/case_name`) и возможность `t.Parallel()`. В хелперах полезен `t.Helper()` (Go 1.9).

## 11.4. Рандомизированное и интеграционное тестирование

* **Рандомизация (Fuzzing / Randomized Testing)**:
  Генерация псевдослучайных входных данных для поиска граничных багов.
  > [!IMPORTANT]
  > Всегда логируйте seed генератора (`t.Logf("Seed: %d", seed)`), чтобы найденный сбой можно было воспроизвести детерминированно.
* **Тестирование CLI-программ (`package main`)**:
  Разделяйте логику вывода `echo(out io.Writer, ...)` и `main()`. В тесте передавайте `out = new(bytes.Buffer)` для перехвата вывода.
* **Тестирование белого ящика (Мокирование с `defer`)**:
  ```go
  func TestQuota(t *testing.T) {
      saved := notifyUser
      defer func() { notifyUser = saved }() // гарантированный откат мока

      notifyUser = func(user, msg string) { /* тестовый стаб */ }
      CheckQuota("user@example.com")
  }
  ```

> [!NOTE]
> **Актуальность (Go 1.18+):** фаззинг встроен в тулчейн и не требует ручного управления seed: 
> ```go
> func FuzzIsPalindrome(f *testing.F) {
>     f.Add("kayak") // seed-кейсы
>     f.Fuzz(func(t *testing.T, s string) { IsPalindrome(s) })
> }
> ```
> Запуск `go test -fuzz=FuzzIsPalindrome`; найденные провальные входы автоматически сохраняются в `testdata/fuzz/` и воспроизводятся обычным `go test`.

## 11.5. Внешние тесты и разрыв циклических зависимостей

Если тест низкоуровневого пакета `net/url` импортирует высокоуровневый `net/http`, возникает запрещенный импортный цикл.

**Решение**:
* Поместить тест в пакет `package url_test` (в файле `url_test.go`).
* `go test` скомпилирует его как отдельный внешний пакет, разорвав цикл.

### Паттерн `export_test.go` (доступ к неэкспортированным сущностям):
Чтобы открыть доступ к неэкспортированной функции `internalHelper` только для внешних тестов `package url_test`:
```go
// Файл export_test.go (виден только во время go test):
package url

var InternalHelper = internalHelper
```

## 11.6. Анализ покрытия кода (Coverage)

```bash
# Генерация отчета о покрытии:
go test -coverprofile=c.out

# Интерактивный HTML-отчет в браузере с подсветкой строк:
go tool cover -html=c.out

# Подсчет частоты выполнения каждого блока инструкций:
go test -covermode=count -coverprofile=c.out
```

> [!NOTE]
> **Актуальность (Go 1.20+):** покрытие доступно и вне тестов: `go build -cover` собирает обычный бинарник, который пишет профили в каталог из переменной `GOCOVERDIR` — так измеряют покрытие реальными интеграционными прогонами.

## 11.7. Бенчмарки производительности (`BenchmarkXxx`)

```go
func BenchmarkIsPalindrome(b *testing.B) {
    for i := 0; i < b.N; i++ {
        IsPalindrome("A man, a plan, a canal: Panama")
    }
}
```

* `b.N` — количество итераций, автоматически подбираемое Go для достижения статистической достоверности (минимум 1 секунда).
* `go test -bench=.` — запуск всех бенчмарков.
* `go test -bench=. -benchmem` — измерение аллокаций памяти (`B/op` — байт за операцию, `allocs/op` — число выделений памяти).

> [!NOTE]
> **Актуальность (Go 1.24+):** предпочтительная форма цикла — `for b.Loop() { IsPalindrome(...) }`: таймеры и число итераций управляются автоматически, а аргументы/результаты не выбрасываются оптимизатором. Классическая форма с `b.N` остаётся валидной.

## 11.8. Профилирование (`pprof`)

```bash
# Сбор профиля CPU или кучи:
go test -run=NONE -bench=MyBenchmark -cpuprofile=cpu.out
go test -memprofile=mem.out

# Интерактивный веб-интерфейс с графом вызовов:
go tool pprof -http=:8080 cpu.out
```

## 11.9. Функции-примеры (`ExampleXxx`)

```go
func ExampleIsPalindrome() {
    fmt.Println(IsPalindrome("kayak"))
    fmt.Println(IsPalindrome("hello"))
    // Output:
    // true
    // false
}
```

1. **Живая документация**: автоматически отображаются в `godoc` и на `pkg.go.dev`.
2. **Проверяемый тест**: комментарий `// Output:` заставляет `go test` сверять реальный вывод в `stdout` с ожидаемым.
3. **Защита от устаревания**: примеры всегда компилируются, поэтому документация никогда не расходится с кодом.
