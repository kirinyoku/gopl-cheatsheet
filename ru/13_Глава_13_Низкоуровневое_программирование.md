## 13.1. Размещение типов в памяти: `unsafe.Sizeof`, `Alignof` и `Offsetof`

Пакет `unsafe` реализуется напрямую компилятором и позволяет исследовать физическое представление данных в памяти.

### Размеры базовых типов (`unsafe.Sizeof`)
Вызов `unsafe.Sizeof(x)` вычисляется во время компиляции (константа типа `uintptr`) и возвращает размер фиксированной части типа в байтах (1 машинное слово = 8 байт на 64-бит, 4 байта на 32-бит):

| Тип данных в Go | Размер в байтах (64-бит) | Внутренняя структура |
| :--- | :--- | :--- |
| `bool`, `int8`, `uint8`, `byte` | 1 байт | Байт |
| `int16`, `uint16` | 2 байта | 2 байта |
| `int32`, `uint32`, `rune` | 4 байта | 4 байта |
| `int64`, `uint64`, `float64` | 8 байтов (1 слово) | 8 байтов |
| `int`, `uint`, `uintptr`, `*T` | 1 слово (8 байт) | Указатель / машинное слово |
| `map`, `func`, `chan` | 1 слово (8 байт) | Указатель на структуру в куче |
| `string` | 2 слова (16 байт) | `ptr` (указатель на байты) + `len` |
| `[]T` (срез) | 3 слова (24 байта) | `ptr` + `len` + `cap` |
| `interface{}` / `any` | 2 слова (16 байт) | `type` (дескриптор типа) + `value` (данные) |

---

### Выравнивание памяти (Alignment) и пробелы (Padding)
Процессор читает память блоками, поэтому адреса данных должны быть кратны их размерам (2 для `int16`, 4 для `int32`, 8 для `int64` и указателей). Для соблюдения выравнивания компилятор вставляет неиспользуемые байты (**пробелы / padding**).

> [!TIP]
> **Оптимизация размера структур**: располагайте поля от самых больших к самым маленьким для минимизации выравнивающих пробелов:
>
> ```go
> // Неоптимально: 24 байта (из-за пробелов выравнивания)
> type Inefficient struct {
>     a bool    // 1 байт + 7 байт пробела
>     b float64 // 8 байт
>     c int16   // 2 байта + 6 байт пробела
> }
>
> // Оптимально: 16 байт (плотная упаковка)
> type Efficient struct {
>     b float64 // 8 байт
>     c int16   // 2 байта
>     a bool    // 1 байт (+ 5 байт пробела в конце)
> }
> ```

* `unsafe.Alignof(x)` — требуемая граница выравнивания адреса типа.
* `unsafe.Offsetof(x.f)` — смещение поля `f` в байтах от начала структуры `x`.

## 13.2. Указатели `unsafe.Pointer` и адресная арифметика

`unsafe.Pointer` — универсальный указатель (аналог `void*` в C), способный содержать адрес любой переменной.

### Схема допустимых приведений:
$$\text{Обычный указатель } *T \longleftrightarrow \text{unsafe.Pointer} \longleftrightarrow \text{uintptr}$$

* `unsafe.Pointer` отслеживается сборщиком мусора (**GC**).
* `uintptr` — обычное число для выполнения адресной арифметики (сложения смещений).

### Идиома адресной арифметики:
```go
// Прямой доступ к полю структуры по смещению:
pb := (*int16)(unsafe.Pointer(uintptr(unsafe.Pointer(&x)) + unsafe.Offsetof(x.b)))
*pb = 42
```

> [!CAUTION]
> **Смертельная ловушка сохранения `uintptr` во временную переменную**:  
> ```go
> // НЕПРАВИЛЬНО:
> tmp := uintptr(unsafe.Pointer(&x)) + unsafe.Offsetof(x.b)
> pb := (*int16)(unsafe.Pointer(tmp)) // ОШИБКА: x могла переместиться в памяти!
> ```
> При росте стека горутины или перемещении объекта сборщиком мусора все `unsafe.Pointer` обновляются автоматически. Число в `uintptr` не обновляется $\to$ запись произойдет в чужую память!  
> *Правило*: все преобразования должны производиться **внутри одного выражения**.

> [!NOTE]
> **Актуальность:** пакет `unsafe` пополнился типобезопасными хелперами для конверсий, покрывающими большинство типовых задач без ручной арифметики с `uintptr`: `unsafe.Slice(ptr, len)` и `unsafe.SliceData(s)` (Go 1.17), `unsafe.String(b, len)` и `unsafe.StringData(s)` (Go 1.20).

## 13.3. Глубокое сравнение циклических структур данных

Для сравнения графов объектов с циклическими ссылками (например, `a.next = a`) адреса посещенных указателей регистрируют в хеш-таблице:

```go
type comparison struct {
    x, y unsafe.Pointer
    t    reflect.Type
}

seen := make(map[comparison]bool)
```

## 13.4. Вызов Си-библиотек (`cgo`)

```go
package bzip

/*
#cgo CFLAGS: -I/usr/include
#cgo LDFLAGS: -lbz2
#include <bzlib.h>
*/
import "C"
import "unsafe"

func CompressInit(stream *C.bz_stream) {
    C.BZ2_bzCompressInit(stream, 9, 0, 30)
}
```

### Правила работы с `cgo`:
1. **Преобразование строк**:
   * Из Go в C: `cs := C.CString(goStr)` — **выделяет память в куче Си**.
   * **Обязательно освобождать**: `defer C.free(unsafe.Pointer(cs))` (для `C.free` нужен `#include <stdlib.h>` в Си-прологе).
   * Из C в Go: `goStr := C.GoString(cs)` — копирует байты в память, управляемую Go.
2. **Типы C**: доступны через префикс `C.` (`C.int`, `C.uint`, `C.char`).

> [!NOTE]
> **Актуальность:** при кросс-компиляции (`GOOS` отличается от хоста) cgo по умолчанию **отключён** — для него требуется Си-тулчейн целевой платформы. Поэтому проекты стараются обходиться без cgo; существует и альтернатива, вызывающая Си-библиотеки без cgo через `dlopen`/`dlsym` — пакет `github.com/ebitengine/purego`.

## 13.5. Предостережение: Опасности `unsafe`

> *«Используйте `unsafe` только тогда, когда это абсолютно необходимо, и скрывайте его за безопасным API пакета».*

### 3 главных риска:
1. **Потеря переносимости**: код становится зависимым от разрядности платформы (32/64-бит) и порядка байтов (Endianness).
2. **Нарушение совместимости**: внутреннее представление типов в будущих релизах Go может измениться, что сломает логику программы.
3. **Повреждение памяти**: ошибки в адресной арифметике вызывают порчу памяти и труднодиагностируемые сбои рантайма.
